### 对 #1 的说明

`Δ = −0x98` 意味着缓冲区从 `T0 − 0x98` 开始往上写 `0x200` 字节：

```
写入范围 = [T0 − 0x98, T0 + 0x168]
覆盖窗口 = [T0 + 0x00, T0 + 0x58]
⇒ 完全包住 ✅
```

### 对 #3 的说明

`Δ = +0x20` 是**零余数对齐**到 `task` 字段的位置，也就是说这 56 字节**恰好**落在
`task(+0x30)` 到 `ww_ctx(+0x58)` 这段上（相对 `T0` 即 `+0x20` 起 0x38 字节）。
**不够覆盖 `tree_entry`/`pi_tree_entry`（`T0+0x00`~`T0+0x28`）**，所以只算部分覆盖。

若利用逻辑只需要改 `lock`（`+0x38`），这一个载体反而是**最精准**的 —— 干扰面最小。

## 方法缺陷（必须知道）

这次扫描基于 **`bl` 调用图**，因此有**固有盲区**：

1. **`_copy_from_user` 被 LTO 完全内联** ⇒ kallsyms 无此符号。真正的 sink 是 `__arch_copy_from_user @ 0xffffffc008fb9300`，需按它重建索引。
2. **`get_user` 系列是内联 `ldtr`** ⇒ 完全不在调用图里，本方法**天然扫不到任何 `get_user` 载体**。想覆盖必须做数据流分析，不是调用图遍历。
3. **驱动 ioctl 路径不可见**：`vfs_ioctl → f_op->unlocked_ioctl` 是**间接调用**，不在 `bl` 图里。要从 `file_operations` 数据段恢复 handler 才能纳入。
   （这也是为什么 #2 号 ashmem 载体是**手工确认**的，不是自动扫出来的。）
