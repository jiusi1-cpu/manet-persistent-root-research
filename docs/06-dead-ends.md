# 06 · 已知死路（别重复踩）

这些是**实际撞过**的墙，记录在此以免后人重复投入。

---

## ⛔ 1. `pselect6` 栈覆盖 —— 最根本的一堵墙

**现象**：6.1 的 `core_sys_select` 用 **`kvmalloc_node` 把 fd 位图分配到堆上**，不在栈上。

**后果**：pselect 的"栈覆盖"手法从物理上就不成立 —— 缓冲区不在栈上，够不到被 free 的 `rt_mutex_waiter`。

```
core_sys_select
  └─ kvmalloc_node(...)     ← 位图在堆，不在栈
       ⇒ 无法用 pselect 的参数缓冲区覆盖 futex 栈帧
```

这是本机型上该 CVE 路线最主要的障碍。

---

## ⛔ 2. Honor `SLIDE_PSELECT_RES_ENCODE` 变通方案 —— 不适用

**方案思路**：绕开 `core_sys_select` 的堆分配，改用同文件里的 `res_*` 栈缓冲。

**为什么不行**：**本内核不存在这些 `res_*` 栈结构。**

⇒ 该变通依赖的具体实现细节在 6.1.118-manet 上不存在，整条路作废。

---

## ⛔ 3. `prctl` —— 几何可以，权限不可达

**几何**：`Δ = +0x08`，长度 ≤ `0x170`（368 B）—— 方向对，但深度/长度都紧。

**致命问题**：反汇编确认 `bl capable`(@`0xd10c4`)**前置**在唯一的 `copy_from_user`(@`0xd1320`) **之前**。

```asm
0xffffffc0080d10c4  bl capable          ← 权限检查在前
...
0xffffffc0080d1320  bl __arch_copy_from_user   ← 唯一的拷贝点
```

⇒ **拷贝发生在权限检查之后，未授权上下文走不到那里。**

**额外打击**：本 build 里连 `PR_SET_MM_MAP` 的 `0x60` 字节拷贝都**不存在** ⇒ 连备选入口都没有。

---

## ⛔ 4. `get_user` 系列 —— 方法盲区，不是候选缺失

**现象**：`get_user` 编译成**内联 `ldtr` 指令**，不产生 `bl`，因此**不在调用图里**。

**后果**：任何基于 `bl` 调用图的扫描（包括本仓库的 `scan.py`）**天然扫不到这一类载体**。

⇒ 这不是"没有这样的载体"，而是"当前方法看不见"。想覆盖**必须做数据流分析**。

---

## ⛔ 5. 驱动 ioctl 路径 —— 间接调用，图里没有

**现象**：

```
__arm64_sys_ioctl → vfs_ioctl → f_op->unlocked_ioctl
                                    ↑ 间接调用
```

**后果**：`f_op->unlocked_ioctl` 不在 `bl` 图里，扫描不到任何驱动层的 ioctl handler。

**解法**：需要从 `file_operations` **数据段**恢复函数指针，才能纳入扫描。
（这也是为什么 ashmem 那个载体是**手工确认**的。）

---

## ⛔ 6. 依赖 `ro.boot.selinux` 判断状态

**现象**：`ro.boot.selinux` 恒读出 `enforcing`，**即便 fastboot 传了 `androidboot.selinux=permissive`**。

**后果**：据此判断"permissive 窗口已关闭"会误判，导致过早放弃。

**正解**：用 **`getenforce`**。

---

## ⛔ 7. 把这个漏洞当成"设计给持久化的"

**认知纠正**：

| | `mqsas` 注入通道 | GhostLock UAF |
|---|---|---|
| 性质 | **厂商主动留下的接口** | 内核竞态 UAF |
| 稳定性 | 高（设计如此） | 低（窗口窄、需精确控堆/栈） |
| 利用代价 | 一行 `service call` | 需要写原语 + 提权链 |

⇒ **能持久化的东西，厂商自己必须留一条"不进 fastboot 也能起来"的路。**
顺着厂商自己留的通道找，往往比硬啃内核漏洞更接近目标。

---

## ⛔ 8. 别用会缓冲输出的管道跑长任务

**现象**：`scan.py` 用 `Select-Object -Last` 缓冲输出，任务被中断时**结果全丢** ——
`hits.json` / `dests.json` **从未生成**，整轮扫描作废。

**正解**：**分阶段落盘，边跑边写文件。**

---

## 🟡 9. 框架接口在提权后依然不可用

`am` / `pm` / `appops` / `settings` 在 `u:r:su:s0` 域全部返回
`Failed transaction (2147483646)`，降权到 `su 2000` 也一样。

⇒ 提权后**不要指望用框架接口**做任何事（禁用包、强制停止、改设置都不行）。
可用手段只有：**内核 / sysfs 节点** + **直接按 PID 杀进程** + **`dumpsys`（只读）**。
